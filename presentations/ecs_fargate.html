🐳 What Are Containers and Why They Matter

Traditional Deployment Problems

Common issues:

  • "It works on my machine" syndrome
  • Environment inconsistencies across dev, staging, prod
  • Slow provisioning and heavy resource usage
  • Dependency conflicts between applications

Container Benefits

Containers solve this:

  • Package app + dependencies together
  • Identical behavior everywhere
  • Start in seconds, not minutes
  • Run many containers on one host
  • Lightweight isolation without full VM overhead

🔶 Amazon Elastic Container Service (ECS)

What is ECS?

  • Fully managed container orchestration service
  • No control plane to install, operate, or scale
  • Deep integration with the AWS ecosystem
  • Supports Docker containers natively

Key Value: ECS removes the heavy lifting of managing container infrastructure so you can focus on your applications

ECS Provides

  • Cluster Management - logical grouping of resources
  • Container Orchestration - scheduling, placement, scaling
  • AWS Integration - IAM, ALB, CloudWatch, ECR, VPC

Who Uses ECS?

  • Samsung, Expedia, Capital One, Duolingo
  • Startups to enterprise-scale production workloads

🆚 ECS Launch Types: Fargate vs EC2

AspectFargate (Serverless)EC2 (Self-Managed)
InfrastructureAWS manages computeYou manage EC2 instances
ScalingAutomatic, per-taskManage instance fleet + tasks
PricingPay per task (vCPU + memory)Pay per EC2 instance
PatchingAWS handles OS patchingYou patch instances
ControlLess (no SSH to host)Full (SSH, custom AMIs)
Best ForMost workloads, simplicityGPU, custom OS, cost optimization at scale

This course uses Fargate - the serverless launch type that lets you focus on your containers without managing servers

🧱 ECS Core Concepts: The Building Blocks

🏗️ Cluster

  • Logical grouping of tasks and services
  • Regional resource (spans multiple AZs)
  • Namespace for your container workloads

📋 Task Definition

  • Blueprint for your application
  • Specifies: container image, CPU, memory, ports
  • Versioned (revisions): my-task:1, my-task:2
  • Can define multiple containers (sidecars)

⚙️ Task

  • Running instance of a task definition
  • One or more containers running together
  • Gets its own ENI (network interface) on Fargate
  • Ephemeral - can be stopped and started

🔄 Service

  • Maintains a desired count of tasks
  • Replaces unhealthy tasks automatically
  • Integrates with load balancers
  • Handles rolling deployments

🔄 ECS Services

What a Service Does

  • Maintains a desired count of running tasks
  • Automatically replaces failed or stopped tasks
  • Integrates with ALB for load balancing
  • Handles rolling deployments when you update the task definition
  • Supports auto-scaling based on CloudWatch metrics

Services are the production workhorse of ECS - they keep your application running reliably

Deployment Strategies

  • Rolling Update (default)
    • Gradually replaces old tasks with new ones
    • Configurable min/max healthy percent
    • Zero-downtime deployments
  • Blue/Green (with CodeDeploy)
    • Deploy new version alongside old
    • Shift traffic instantly
    • Easy rollback capability

🌐 Container Networking: awsvpc Mode

How It Works

  • Each task gets its own Elastic Network Interface (ENI)
  • Tasks have their own private IP address
  • Security groups apply at the task level
  • Behaves like an EC2 instance on the network

awsvpc is required for Fargate - every Fargate task automatically gets its own ENI

Network Architecture

  VPC (172.31.0.0/16)
  ├── Subnet A (us-east-1a)
  │   ├── ENI ── Task 1 (nginx)
  │   │         Private IP: 172.31.1.10
  │   └── ENI ── Task 2 (nginx)
  │             Private IP: 172.31.1.11
  └── Subnet B (us-east-1b)
      └── ENI ── Task 3 (nginx)
                Private IP: 172.31.2.10

🔒 Security Groups for ECS

ALB Security Group

# Allow internet traffic to ALB
resource "aws_security_group" "alb_sg" {
  vpc_id = data.aws_vpc.default.id

  ingress {
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

ECS Tasks Security Group

# Only allow traffic FROM the ALB
resource "aws_security_group" "ecs_sg" {
  vpc_id = data.aws_vpc.default.id

  ingress {
    from_port       = 80
    to_port         = 80
    protocol        = "tcp"
    security_groups = [
      aws_security_group.alb_sg.id
    ]
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

Security Pattern: Internet → ALB (SG allows 0.0.0.0/0:80) → Tasks (SG allows only ALB SG)

🔐 IAM Roles for ECS

Task Execution Role

  • Used by the ECS agent (not your code)
  • Pulls container images from ECR
  • Writes logs to CloudWatch
  • Retrieves secrets from Secrets Manager
  • AWS provides: ecsTaskExecutionRole

Think of it as: What permissions does ECS need to run my container?

Task Role

  • Used by your application code inside the container
  • Access S3, DynamoDB, SQS, etc.
  • Scoped to individual tasks (credential isolation)
  • Auditable via CloudTrail

Do not confuse these two roles! Execution role = ECS infrastructure. Task role = your application's AWS permissions.

⚖️ Application Load Balancer Integration

Why Use an ALB with ECS?

  • Single DNS entry for your service
  • Health checks - automatically routes away from unhealthy tasks
  • Distribution - spreads traffic across tasks
  • Dynamic port mapping - ALB handles port allocation
  • Content-based routing - route /api to one service, /web to another

Key Benefit: One ALB can serve multiple ECS services using path-based or host-based routing rules

ALB Components

  • Listener - checks for connection requests (port 80)
  • Target Group - routes requests to registered targets
  • Health Check - verifies targets are healthy
Internet ──▶ ALB (Listener :80)
                │
                ▼
           Target Group
          (type: ip)
            │       │
            ▼       ▼
         Task 1   Task 2
        (nginx)  (nginx)

🎯 Target Groups for Fargate

Key Configuration

  • Target type must be ip (not instance) for Fargate
  • ECS automatically registers/deregisters task IPs
  • Health check verifies each task is responding

Health Check Settings

SettingValue
Path/
Healthy threshold2
Unhealthy threshold3
Interval30 seconds

Terraform Code

resource "aws_lb_target_group" "tg" {
  name        = "my-target-group"
  port        = 80
  protocol    = "HTTP"
  vpc_id      = data.aws_vpc.default.id
  target_type = "ip"  # Required for Fargate
}

resource "aws_lb_listener" "listener" {
  load_balancer_arn = aws_lb.alb.arn
  port              = 80
  protocol          = "HTTP"

  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.tg.arn
  }
}

🔗 ECS Service with Load Balancer

How It Works

  • ECS service registers task IPs with the target group
  • When tasks start, they are registered; when they stop, they are deregistered
  • Rolling deployments: new tasks register before old tasks drain
  • ALB only sends traffic to healthy tasks

Zero-downtime deployments - ECS drains connections from old tasks only after new tasks pass health checks

Service Configuration

resource "aws_ecs_service" "nginx" {
  name            = "my-service"
  cluster         = aws_ecs_cluster.main.id
  task_definition = aws_ecs_task_definition.nginx.arn
  launch_type     = "FARGATE"
  desired_count   = 2

  network_configuration {
    subnets          = data.aws_subnets.default.ids
    security_groups  = [aws_security_group.ecs_sg.id]
    assign_public_ip = true
  }

  load_balancer {
    target_group_arn = aws_lb_target_group.tg.arn
    container_name   = "my-container"
    container_port   = 80
  }

  depends_on = [aws_lb_listener.listener]
}

📍 Task Placement and Scheduling

Fargate Placement

  • Fargate handles placement automatically
  • Spreads tasks across Availability Zones
  • No need to manage instance capacity
  • Tasks run in your VPC subnets

With Fargate: You specify CPU, memory, and subnets. AWS handles everything else.

📊 CloudWatch Integration

CloudWatch Logs

  • awslogs driver sends container stdout/stderr to CloudWatch
  • Log Group: /ecs/task-family
  • Log Stream: one per task (stream prefix + container + task ID)
  • Configured in the task definition
"logConfiguration": {
  "logDriver": "awslogs",
  "options": {
    "awslogs-group": "/ecs/my-task",
    "awslogs-region": "us-east-1",
    "awslogs-stream-prefix": "ecs"
  }
}

Container Insights

  • CPU and memory utilization per task and service
  • Network throughput metrics
  • Running task count over time
  • Enable at the cluster level

ECS Events (EventBridge)

  • Task state changes (PENDING → RUNNING → STOPPED)
  • Service deployment events
  • Container instance state changes
  • Use for alerting, triggering Lambda, custom schedulers

📈 Scaling ECS Services

Manual Scaling

  • Change desired_count on the service
  • ECS launches or terminates tasks to match
  • Console: Service → Update → Desired tasks
  • Terraform: change desired_count, apply

Auto Scaling

  • Target Tracking: maintain a target metric value
  • Step Scaling: scale based on CloudWatch alarm thresholds
  • Scheduled: scale at specific times

🏗️ Module 3: Infrastructure as Code for ECS

From Clicks to Code

Automating ECS deployments with Terraform

❓ Why Infrastructure as Code for Containers?

Manual Console Problems

  • Configuration drift - environments diverge over time
  • No repeatability - can you recreate this setup exactly?
  • No version control - who changed what, when?
  • Error-prone - miss a setting and spend hours debugging
  • Tedious cleanup - delete resources in the right order

IaC Benefits

  • Reproducible - same config, same result every time
  • Version controlled - Git history shows all changes
  • Reviewable - code reviews for infrastructure
  • Self-documenting - the code IS the documentation
  • One-command cleanup - terraform destroy

🔧 Terraform Overview

What is Terraform?

  • Open-source IaC tool by HashiCorp
  • Declarative - describe what you want, not how
  • Provider-based - AWS, Azure, GCP, and 3000+ more
  • Tracks state to know what exists

Key Concepts

  • Provider - plugin for a cloud/service (e.g., aws)
  • Resource - infrastructure to create (e.g., aws_ecs_cluster)
  • Data Source - read existing infrastructure
  • State - tracks what Terraform manages

The Terraform Workflow

# 1. Initialize (download providers)

$ terraform init


# 2. Preview changes

$ terraform plan


# 3. Apply changes

$ terraform apply


# 4. Destroy everything

$ terraform destroy

Always plan before apply! Review what will change before making changes.

Provider Configuration

  }
}

provider "aws" {
  region = "us-east-1"
}

Data Sources (Read Existing Resources)

# Look up the default VPC
data "aws_vpc" "default" {
  default = true
}

# Look up subnets in the default VPC
data "aws_subnets" "default" {
  filter {
    name   = "vpc-id"
    values = [data.aws_vpc.default.id]

# Look up existing IAM role
data "aws_iam_role" "ecs_execution_role" {
  name = "ecsTaskExecutionRole"

🔗 Resource Dependencies in Our Config

  Dependency Graph (Terraform creates resources in this order):

  data.aws_vpc.default ──────────┐
  data.aws_subnets.default ──────┤
  data.aws_iam_role.ecs_exec ────┤
                                 │
  aws_security_group.alb_sg ─────┼──▶ aws_lb.alb ──▶ aws_lb_listener
  aws_security_group.ecs_sg ─────┤                        │
                                 │   aws_lb_target_group ──┘
  aws_ecs_cluster.main ──────────┤
  aws_ecs_task_definition.nginx ─┤
                                 │
                                 └──▶ aws_ecs_service.nginx_service
                                      (depends_on: aws_lb_listener)

Implicit Dependencies

  • Terraform detects references between resources
  • aws_lb.alb references aws_security_group.alb_sg.id
  • Terraform automatically creates the SG first

Explicit Dependencies

  • depends_on forces ordering when there's no direct reference
  • The ECS service uses depends_on = [aws_lb_listener.listener]
  • Ensures the listener exists before the service tries to register

💾 Terraform State and ECS

What State Tracks

  • Resource IDs - which AWS resources belong to this config
  • Attributes - current values (ARN, DNS name, etc.)
  • Metadata - dependencies and provider info
  • Stored in terraform.tfstate (local file)

Never manually edit state files! Use terraform state commands instead.

Useful State Commands

# List all managed resources

$ terraform state list

aws_ecs_cluster.main

aws_ecs_service.nginx_service

aws_lb.alb

...


# Show details for a resource

$ terraform state show aws_lb.alb

dns_name = "user0-alb-123.us-east-1..."

👤 The user0 Naming Convention

Every resource in main.tf uses user0 as a prefix. Before deploying, replace it with your assigned username.

#ResourceOriginal NameYour Name (e.g., user5)
1ECS Clusteruser0-clusteruser5-cluster
2ALB Security Groupuser0_ALBuser5_ALB
3ECS Security Groupuser0_ECSuser5_ECS
4ALBuser0-albuser5-alb
5Target Groupuser0-target-groupuser5-target-group
6Task Definitionuser0-taskuser5-task
7ECS Serviceuser0-serviceuser5-service

🔄 Modifying ECS Infrastructure with Terraform

In-Place Update (No Downtime)

Changing desired_count updates the service without replacing it:

# Before
desired_count = 1

# After
desired_count = 3

$ terraform plan

~ aws_ecs_service.nginx_service

  ~ desired_count: 1 -> 3

Plan: 0 to add, 1 to change, 0 to destroy

Replacement (New Revision)

Changing CPU/memory creates a new task definition revision:

# Before
cpu    = "256"
memory = "512"

# After
cpu    = "512"
memory = "1024"

$ terraform plan

-/+ aws_ecs_task_definition.nginx

~ aws_ecs_service.nginx_service

Plan: 1 to add, 1 to change, 1 to destroy

💥 Terraform Destroy: Clean Teardown

How Destroy Works

  • Destroys resources in reverse dependency order
  • Service first (deregisters tasks from target group)
  • Then ALB, target group, listener
  • Then security groups, cluster, task definition
  • Requires confirmation (yes)

$ terraform destroy

Plan: 0 to add, 0 to change, 8 to destroy

Do you really want to destroy? (yes)

📝 Course Recap: ECS Concepts

Core Architecture

  • Cluster - logical grouping of tasks and services
  • Task Definition - blueprint (image, CPU, memory, ports)
  • Task - running instance of a task definition
  • Service - maintains desired count, handles deployments
  • Fargate - serverless compute, no servers to manage

Production Patterns

  • ALB - single DNS, health checks, traffic distribution
  • Security Groups - ALB SG + ECS SG layered security
  • IAM Roles - execution role vs task role
  • awsvpc - each task gets its own ENI
  • Scaling - manual (desired_count) or auto scaling
  • Logging - CloudWatch Logs with awslogs driver
